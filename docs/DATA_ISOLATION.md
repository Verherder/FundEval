# FundEval 多用户数据隔离说明

## 1. 目标和基本规则

FundEval 使用一个共享基金池，同时隔离每个用户的个人投资数据：

- 管理员维护的 `fund_catalog` 构成公共基金池，行情刷新只需要按基金代码处理一次。
- 所有用户都能浏览公共基金池，并从中添加自己的自选基金。
- 每个用户的基金主表展示完整公共基金池，但只叠加当前用户自己的持有状态、份额和默认图表。
- 基金客观数据可以共享；用户的交易、份额、持仓和收益不能共享。
- 后端只从已认证的 Flask Session 取得 `user_id`，不信任请求参数中的用户 ID。

数据隔离由应用服务和带 `user_id` 的 SQL 条件共同保证。SQLite 本身没有行级安全策略，新增个人数据接口时必须继续遵守本文的所有权检查规则。

## 2. 数据边界

### 2.1 共享数据

| 数据 | 存储位置 | 说明 |
| --- | --- | --- |
| 基金代码、名称、基金 key | `fund_catalog` | 同一基金只保存一份 |
| 成立日期、行业标签 | `fund_catalog` | 行业标签只有管理员可修改 |
| 估值 1、估值 2 历史 | `fund_catalog` | 行情刷新结果对所有自选该基金的用户复用 |
| 基金历史净值 | `fund_nav_history` | 按基金代码和日期共享 |
| 基金业绩曲线缓存 | `fund_performance_curve_cache` | 表示基金自身表现，不含个人交易 |
| 指数净值 | `index_nav_history` | 沪深 300 等公共基准数据 |

所有登录用户都能在基金主表和公共基金池接口浏览这些基金。查询使用
`fund_catalog LEFT JOIN user_watchlist`；没有当前用户关联时显示为未持有、0 份额，
且只读浏览不会自动创建个人关联。

### 2.2 个人数据

| 数据 | 存储位置 | 隔离规则 |
| --- | --- | --- |
| 自选基金关系 | `user_watchlist` | 唯一键为 `(user_id, fund_code)` |
| 持有状态、份额、默认图表 | `user_watchlist` | 查询和修改必须同时带当前 `user_id` |
| 买入、卖出、分红记录 | `fund_transactions` | 只允许读取和修改当前用户记录 |
| 待确认买入 | `fund_pending_buys` | 结算时同时校验记录 ID 和 `user_id` |
| 个人收益、持仓收益曲线 | 运行时计算 | 只使用当前用户交易、份额和共享净值 |
| 交易导入任务和进度 | 导入任务状态 | 任务记录保存所有者，其他用户查询时返回不存在 |
| 基金列表和交易导出 | 临时响应文件 | 只导出当前用户数据，响应完成后删除临时文件 |

交易平台订单号只要求在单个用户内唯一，数据库约束为 `(user_id, order_no)`。不同用户从同一平台导入相同订单号不会互相冲突。

## 3. 请求和权限流程

个人接口遵循以下流程：

1. `@login_required` 确认 Session 中存在登录用户。
2. 路由调用 `get_current_user_id()` 取得用户 ID。
3. Service 将该 ID 传给 Repository/Database，不接受前端指定其他用户。
4. 读取使用 `WHERE user_id = ?`；更新和删除同时使用资源 ID、基金代码和 `user_id`。
5. 资源不存在或不属于当前用户时，不返回其他用户的信息。

基金目录和行业标签属于共享数据，其修改与基金本体删除操作必须使用
`@admin_required`。数据库通过 `users.is_admin` 判断管理员；旧数据迁移时仅将
`jiaming` 设置为管理员，不能依赖用户名字符串在接口中硬编码授权。普通用户取消
自选只能删除自己的 `user_watchlist` 关联，不能删除 `fund_catalog`。

交易导入进度必须携带任务 ID 和当前用户 ID。即使其他用户获取了任务 ID，也不能读取任务状态、失败行或统计结果。导入日志不得记录订单号、金额、份额或完整原始行。

### 3.1 权限矩阵

| 功能 | 普通用户 | 管理员 |
| --- | --- | --- |
| 浏览公共基金池 | 允许 | 允许 |
| 加入或取消自己的自选 | 允许 | 允许 |
| 管理自己的交易、份额和收益 | 允许 | 允许 |
| 按基金代码新增公共基金 | 允许 | 允许 |
| 覆盖性导入基金列表 | 禁止 | 允许 |
| 修改共享行业标签和成立日期 | 禁止 | 允许 |
| 打开设置页、修改全局刷新配置 | 禁止 | 允许 |
| 回填成立日期 | 禁止 | 允许 |
| 清空单只或全部交易记录 | 禁止 | 允许 |
| 生成注册邀请码 | 禁止 | 允许 |
| 查看和管理用户账号 | 禁止 | 允许 |

设置入口和敏感按钮会对普通用户隐藏，但隐藏不作为安全边界；对应页面和 API
仍通过 `@admin_required` 或等价的服务端授权返回 `403`。全局刷新配置的有效值需要被
所有登录用户读取以执行页面自动刷新，但只有管理员可以修改。

管理员可在设置页生成有效期为 1 到 30 天的一次性邀请码。响应只显示一次明文令牌，
数据库仅保存 SHA-256 哈希；邀请码注册成功后立即标记为已使用。

管理员可在设置页查看用户、授予或撤销管理员、锁定或解锁账号、重置密码。系统禁止
管理员锁定自己或修改自己的管理员身份，并保证至少保留一个管理员。锁定账号时撤销
该用户尚未使用的记住登录令牌。

## 4. 页面和曲线行为

- 基金主表以 `fund_catalog` 为入口，左连接当前用户的 `user_watchlist`；没有个人状态的基金仍然可见。
- 持仓汇总、交易、份额和个人收益只读取当前用户的 `user_watchlist` 与交易记录。
- 公共基金池选择器读取全部 `fund_catalog`，并标记当前用户是否已经自选。
- 刷新一个基金的估值后，共享目录中的结果可供所有自选该基金的用户使用，但不会自动把该基金加入其他用户自选。
- 基金业绩曲线只使用共享净值和指数数据，因此可以共享缓存。
- 个人收益曲线必须按当前用户交易时间线计算，禁止保存或复用其他用户计算结果。
- 用户删除自选基金时只删除自己的关联，不删除其他用户关联、共享基金元数据或历史净值。

## 5. 注册和初始数据

系统采用单次邀请码注册。邀请码只保存哈希，必须未过期、未撤销且未使用。

用户名必须匹配 `[A-Za-z0-9_]{3,20}`。密码必须为 12 到 20 位，并且只允许字母、
数字及 `@#$%^&*_.!+-`。所有数据库查询继续使用参数绑定；正则是输入约束，不能替代
参数化 SQL 的注入防护。

新用户创建后没有默认自选、份额、交易或收益。用户登录后从公共基金池选择基金；
选择只会创建本人的 `user_watchlist` 关联。

## 6. 旧数据库迁移

应用不会在启动时自动改表或复制 `fund_map.json`。检测到旧数据库时会拒绝创建空运行库，并提示执行显式迁移：

```bash
./scripts/fundctl.sh migrate --dry-run
./scripts/fundctl.sh migrate
```

迁移规则：

- 将所有旧 `user_funds` 按基金代码合并为公共基金目录；同一基金的共享字段冲突时优先采用 `jiaming` 的记录。
- `jiaming` 作为管理员管理公共基金池，但管理员权限不等于自选关系；迁移不会自动增加管理员自选。
- 保留每个用户原有的自选、份额、图表默认项、交易和待确认买入，不跨用户复制个人字段。
- 将订单号唯一约束调整到用户范围。
- 保留用户 ID、用户名、密码哈希和创建时间，不强制重置密码。
- 保留旧自选记录 ID、顺序和份额原始精度，不对份额做迁移期舍入。
- 整体迁移在事务中完成；执行前创建一致性数据库备份，失败时回滚。
- 提交事务前逐条比较旧自选和新自选的用户、基金、持有状态、份额和默认图表；
  任一字段不一致都会终止并回滚迁移。

迁移完成后至少验证：每个用户的自选数量、`jiaming` 交易数量、其他用户交易数量、管理员数量以及个人收益曲线。

## 7. 开发检查清单

新增或修改个人功能时必须检查：

- 查询、更新、删除是否都使用当前 `user_id`。
- 是否存在只凭递增资源 ID 就能读取或修改数据的接口。
- 缓存 key 是否包含用户 ID，或者缓存内容是否确实属于共享数据。
- 导入、导出、后台任务和临时文件是否保留了用户所有权。
- 日志和错误信息是否泄漏金额、订单号、份额、令牌或其他用户存在性。
- 测试是否至少包含两个用户，并验证同一基金共享行情但不共享交易和份额。

现有隔离回归测试位于 `tests/test_security_isolation.py`。
